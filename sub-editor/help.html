Sub Editor Reference

Everything the inspector's fields actually do, object type by object type, with worked examples. This is a reference, not a tutorial - jump to whatever section matches what you're building via the sidebar.

See also: ClaudeDocs/Master Design Doc Rev1 Core Principles.md for the compartment/station/tool interaction model this editor's output is meant to support in-game, and ClaudeDocs/Sub Editor.md for the original design brainstorm this tool grew out of.

Overview & Workflow

The Sub Editor produces plain JSON room layouts. Each object in a room declares four things and nothing else: what it looks like (a sprite or a plain shape), where it is (position, rotation, scale), how a player interacts with it (click, drag, or nothing), and what game value it reads or writes (a Binding to send, a State/Output Binding to read back). It never contains game logic - the actual submarine game client (client/) loads the exported JSON and does the simulating.

The normal workflow:

  1. Point Choose Assets Folder... at a folder of PNGs (or use Load Images... to pick files by hand). One level of subfolders becomes asset categories automatically.
  2. Drag an asset from the Asset Library onto the canvas, or use one of the ADD buttons (Placeholder Object, Player Spawn, Scope Object, Indicator Light) for something that isn't a sprite yet.
  3. Select it and configure it in the Inspector on the right: transform, interaction, output, visual states, binding.
  4. Repeat for every control/gauge/decoration a room needs. Group related pieces (Ctrl+G) and save frequently-reused ones as Prefabs.
  5. Export Room (or Export All Rooms) to produce the JSON the game client loads.

Assets vs. Objects: an asset is just an image file sitting in the library. An object is a thing placed in a room, referencing an asset (or a plain color) plus everything above. The same asset (lever_body.png) can back many different objects with different bindings, ranges, and rotations.

Removing old/redundant assets: the 🗑 button on an asset's own row (or Delete in the bulk-select bar, after selecting several with shift-click) permanently removes it from the library. If anything still references it, you'll be warned before deleting - a removed asset's id just stops resolving afterward, so any object/prefab still pointing at it falls back to its plain colored shape rather than breaking. Not covered by Undo, so use Save Project Backup first if unsure.

Rooms, Stations & Layers

Rooms

A room is a compartment (Forward Torpedo, Information, Control Room, Engineering by default - add more with + New Room). Switch rooms with the Room dropdown in the top bar. A room's own object list is what a player sees looking around that compartment - stations are selected from there, not shown inline.

Stations

A station (Helm, Sonar, the Torpedo Data Computer, ...) is its own separate object list, a full peer of the room's compartment view - not a sub-area of it. Switch between "editing the compartment" and "editing one station's own screen" with the View dropdown next to Room. + New Station prompts for a display name and derives an ID from it (e.g. "Sonar" → station_sonar); Rename Station lets you separately edit the display name and the ID (the ID is what the game client/server actually key off of, so it has to match exactly what they expect - some real station IDs intentionally skip the station_ prefix, like nav_map or torpedo_tube).

Example
Building the Torpedo Data Computer screen: set Room to "Forward Torpedo", then View to "Torpedo Tube" (or create it via + New Station if it doesn't exist yet). Everything you place now - the TDC scope, the gyro/spread dials, the tube arm lights - lives on that station's own screen, separate from whatever decorations sit in the Forward Torpedo compartment itself.

Layers

Layers group objects within one room/station for organization, selective hiding, and export optimization. Every container starts with a default layer. + New Layer adds another; unchecking a layer's visibility checkbox both hides it and drops any of its objects out of the current selection (effectively locking it against accidental edits). Checking Flatten on Export for a layer rasterizes every object on it into one baked image at export time - useful for static background/decoration layers with many small pieces, since the game client then draws one image instead of dozens of separate draw calls. Flattening only ever affects the exported JSON, never the live editor view.

Object Types

Decoration / Station / Control / Tool Target

The Object Type dropdown (Decoration, Station, Control, Tool Target) is presentational bookkeeping for your own organization - none of these four values change what fields are available or how the object behaves. What actually determines behavior is the object's Interaction and Output settings below, independent of this dropdown. Everything you drag from the Asset Library or add as a Placeholder starts as decoration.

Group

Select 2+ objects and press Ctrl+G (or the Group button in the multi-select panel) to combine them into one Group object, positioned at their combined center. Double-click a group on canvas to enter Object Edit Mode - everything else dims and locks while you reposition the group's own pieces - then ← Back to Room to recollapse it. Groups can be saved as Prefabs too.

Player Spawn

Invisible in the actual game - just a position + facing marker for where a player's avatar should appear. Spawn Type is either Room Enter Spawn (where a player appears on entering this room) or Station Link (where their avatar stands when they open a particular station - pick which one via the Station dropdown that appears). Rotation sets which way the avatar faces.

Scope

A scope object is a blank shape in the editor - like a green screen - that a fully server-driven live display gets projected onto in-game, filling the object's own bounds. There's nothing to preview here since the real content depends on live server state; you're only authoring its position, size, and shape.

FieldMeaning
ShapeCircular or Rectangular - clips the live content to that shape.
Display ChannelWhich live view to project: sonar, nav_map, tdc, periscope, or weatherdeck (the last one currently renders a "NOT YET IMPLEMENTED" placeholder in-game). Free text with autocomplete, not a fixed dropdown, so a new channel can be added on the client side without an editor change.
Fill %How much of the object's own width/height the live content actually fills (0.1-1) - leaves a border of whatever's behind it otherwise.
Range (nav_map)World units from the ship shown at the scope's outer edge - match this to how zoomed in/out the chart should read.
Range (sonar)World units at the scope's outer edge - match this to the server's own sonar_max_range export so a contact plots closer to center the nearer it actually is. A rotating compass ring (ticks every 10°, labeled every 30°, N/E/S/W at the cardinals) runs around the inside of the rim - the numbers stay clean true-compass values while the ring itself turns as the sub's heading changes, same gyrocompass-repeater-card convention as a real sonar/periscope readout (the lubber line at top - dead ahead - stays fixed; the card underneath rotates).
Pulse Speed Scale (sonar)Shrinks sonar.pulse_hz for the ring-pulse animation, same idea as an Output gauge's Wobble Speed Scale below - keeps the scope's pulse feel consistent with any gauge wired to the same value.
Range / Speed / Turn Rate / Gyro Activation Distance / Gyro Limit (tdc)The Torpedo Data Computer's predicted-path plot - a full circle, with the sub inset near the bottom rim rather than dead center so the plotted range can use almost the full diameter; tracks only ever appear in the top portion since the gyro can't aim past +/-Gyro Limit. A torpedo is aimed by a CONTINUOUS gyro deflection, not a target heading it turns to and stops at: past Gyro Activation Distance it holds a constant turn (like a rudder held at a fixed angle) for the rest of its flight, at Turn Rate scaled by how far its own gyro/spread setting sits within +/-Gyro Limit - it never straightens out on its own. These five match the server's torpedo_speed * (torpedo_max_lifetime_ticks / 60), torpedo_speed, torpedo_turn_rate, torpedo_gyro_activation_distance, and tdc_gyro_limit exports respectively - keep them in sync if those are retuned. Reads live tdc (gyro_angle/spread_angle) and torpedo_tubes state to draw one predicted track per tube, bright for armed tubes, plus a yellow dot for each actually-fired torpedo still in flight (from the top-level torpedoes broadcast's bearing_relative/distance - the same live markers the nav_map channel shows, just plotted bow-relative instead of on the compass chart).
Field of View° / Reference Distance (periscope)A flat horizon-strip stand-in for the eventual full 3D periscope view, drawn to fit its CIRCULAR port (not the full rectangular bounding box - anything near a corner would fall outside the actual visible ellipse). Sky/sea gradient, a horizon line, an absolute compass bearing centered near the top (degrees plus the nearest of the 8 compass points, e.g. 302NW), a relative bearing centered near the bottom (degrees off the sub's own bow plus its quadrant - SB starboard bow, SA starboard aft, PA port aft, PB port bow, e.g. 045SB), and a scaled silhouette for every optically-visible ship (any convoy) that currently falls within Field of View of the look direction - a convoy can show several silhouettes at once, side by side, not just one. A torpedo hit doesn't make a ship vanish outright: it triggers a brief explosion flash (client-local, one-shot) and the ship then spends several seconds (the server's ship_sink_duration) tilting and settling lower before finally disappearing, driven by that contact's own sinking/sink_progress fields so every viewer sees the same animation in sync. periscope.bearing itself turns right along with the sub's own heading for free, same as a real periscope mounted to the hull - the bearing dial only changes the OFFSET off the bow, not the absolute direction directly. Field of View is the total angular width visible at once, centered on periscope.bearing - keep it narrow (a real scope is a zoomed, magnified view) so a contact only appears once the bearing dial is swept close to it, the same "sweep to find it" feel as sonar. It also responds to the same wheel-scroll/pinch zoom gesture every scope already supports (see the Navigation Map's own zoom/pan) - zooming in narrows the effective field of view AND enlarges contact silhouettes to match, real angular magnification rather than just spreading things across a tighter slice of screen. Reference Distance is a pure rendering scale (never sent to/from the server): a contact at exactly that distance draws at its authored base silhouette size, closer bigger, farther smaller. Deliberately reads only plain physical facts from the server (periscope.available/bearing plus a contacts list of type/bearing_true/distance, no precomputed screen position) so a future real 3D view can consume the exact same state - only this drawing function would ever need replacing.
Example
A circular sonar scope on the Sonar station: Shape = Circular, Display Channel = sonar, Fill % = 0.95, Range = 200 (matching the server's sonar_max_range).
Example: TDC scope
On a Torpedo Data Computer station (e.g. in the Conning Tower): Shape = Circular, Display Channel = tdc, Range = 1000, Speed = 20, Turn Rate = 45, Gyro Activation Distance = 50, Gyro Limit = 90 (matching the server's current Torpedo export defaults).
Example: Attack Periscope
On the Attack Periscope station (Conning Tower): Shape = Rectangular, Display Channel = periscope, Field of View = 20, Reference Distance = 500. Bind a Drag (Rotate) control's Binding to SET_PERISCOPE_TURN (Value Min -1 / Max 1) - unlike the Sonar dial, this is steering-wheel style: the handle's deflection is a held turn RATE, not an absolute bearing, so also check Spring to Center on Release and set a small Deadzone (both in the Interaction section) so the scope keeps turning while the handle is held over and stops cleanly the instant it's let go.

Leak Zone / Fire Zone

Not placed via the Object Type dropdown - use the Paint Leak Zone / Paint Fire Zone tools instead (set Brush Size first, then drag across the canvas; click the tool again or press Escape to stop painting). Each stroke is one zone object: a growing list of points plus a radius, defining where the server may spawn that kind of damage. The Radius field in the inspector and the point count are the only editable properties afterward. Toggle their visibility in the editor (not in-game) via the META LAYERS checkboxes.

Indicator Light (preset)

+ Indicator Light is a shortcut, not a distinct object type - it drops an ordinary round object with Visual States pre-enabled and three starter colors (no textures needed): empty (dull dark green), loaded (bright green), and armed (bright red). Rename/add/recolor states afterward exactly like any other object's states; the preset just saves the setup steps for the common case of a small colored status light.

Example: one light per torpedo tube
Click + Indicator Light four times (one per tube). For each one, set State Binding to that tube's own state path: torpedo_tubes.0.state, torpedo_tubes.1.state, torpedo_tubes.2.state, torpedo_tubes.3.state. Each light then independently shows dark green/bright green/red as that specific tube goes from empty to loaded to armed - no textures imported at all.

Transform: Position, Rotation, Scale, Pivot

Every non-zone object has X/Y (world position within the 960×540 room), Rotation°, and Scale X/Scale Y (check Uniform Scale to link them so dragging one drags both). Pivot X/Pivot Y (0-1 each) sets the object's own rotation/scale origin and anchor point within its own width/height: 0,0 is top-left, 0.5,0.5 is center, 1,1 is bottom-right. Drag the orange dot shown on a selected object to set it visually instead of typing numbers.

Example
A wall-mounted gauge needle should spin around its base, not its center: set Pivot Y close to 1 (bottom) so Rotation sweeps the needle's tip through an arc above its mount point instead of spinning in place.

Objects also carry a Placeholder Color and, for a round object, the same circle/rectangle preview shape used by Scope and Indicator Light objects - this is what renders (in-editor and in-game) whenever the object has no sprite asset assigned, or whenever the active Visual State has no sprite of its own (see Visual States).

Interaction Types

Set via the Interaction > Type dropdown. This is what turns a static picture into something a player can operate.

Click

A single tap/click fires the object's Binding action once. Combine with Toggle Switch below for an on/off control instead of a one-shot trigger.

Example
A FIRE torpedo button: Interaction = Click, Binding = FIRE_TORPEDO (a trigger action - no payload, no range fields needed).

Drag (Linear)

FieldMeaning
AxisVertical or Horizontal - which direction the control physically slides.
Min / MaxThe real game value range sent to the server as the handle moves end to end.
ReverseFlips which physical end corresponds to Min vs. Max.
Snap PositionsQuantizes the drag to a fixed number of evenly-spaced stops (Steps, 2-20) instead of a continuous range. Once generated, drag each stop's own point along the path on canvas to fine-tune it off the even spacing.
Visual Travel Min/MaxHow far the sprite itself physically slides on screen (in canvas units), independent of the Min/Max game-value range above - lets a handle travel 40px while sending 0-100 to the server, for instance.
PreviewA slider that scrubs the control through its range in the editor without dragging it by hand, to check the artwork/travel look right.
Example
A throttle lever: Interaction = Drag (Linear), Axis = Vertical, Min = 0, Max = 1, Binding = SET_THROTTLE, Visual Travel Min/Max set to however far the handle should slide up the rail in canvas pixels.

Drag (Rotate)

FieldMeaning
Min / MaxThe real game value range across the control's full sweep.
ReverseFlips rotation direction.
Snap PositionsSame quantized-stops mechanism as Drag (Linear), spaced around the arc instead of along a line.
Visual Rotation Min/Max°How far the sprite itself actually turns on screen, independent of the game-value Min/Max - e.g. a wheel that visually turns -120° to +120° while sending a rudder value of -1 to +1.
Infinite RotationFor a compass-style dial that can spin through any number of full turns with no end stops, instead of clamping at Visual Rotation Min/Max. The real game value still wraps within Min/Max (e.g. 0-360) rather than clamping.
Example
A rudder wheel: Interaction = Drag (Rotate), Min = -1, Max = 1, Visual Rotation Min/Max = -120°/120°, Binding = SET_RUDDER. A sonar tuning dial, by contrast, would check Infinite Rotation with Min = 0, Max = 360 and Binding = SET_SONAR_DIAL, so it can be spun all the way around instead of stopping at an end.

Drag (H-Pattern)

A free-form graph of named rest positions ("nodes"), each offset from the object's own X/Y and each carrying whatever value gets sent to the server when the control rests there - a number or a string (e.g. forward). Not limited to a literal H shape: build any T/star/line layout the control actually needs. + Add Node adds one; drag a node on canvas to reposition it. Click a node to set it as the anchor, then shift-click another to connect/disconnect them (drawing the rails a player can slide the handle along); shift-click the same pair again to toggle the connection back off. The node marked with * is the control's current resting position.

Example
An engine order telegraph with FULL/HALF/SLOW/STOP/REV positions: add five nodes roughly along a vertical line, connect each to its neighbor so the handle can only slide between adjacent positions, and set each node's Value to the number or string SET_ENGINE_ORDER (or a gear action) expects at that position.

Open Station

Clicking the object opens a station's dedicated screen (the compartment → station UI model). Pick which station via the Target Station dropdown that appears - no Binding/Payload Key fields apply here, since this doesn't send a game action, it just navigates the local UI.

Touch Hitbox

Shown for any interaction type other than None. Auto-generated the first time an object becomes interactive, padded out from the visual sprite size (minimum ~44px, the standard mobile touch-target guideline) so a tiny sprite still has a comfortably tappable target. Width/Height and Offset X/Offset Y let you enlarge or reposition the tap/drag target independently of how big the artwork actually looks.

Output (Gauge / Wired Display)

Independent of Interaction - an object can be purely an output (a gauge with no interaction), purely an input (a lever with no output), or both at once (a lever whose own handle also visually reflects the live server value, in case another player moves it). Set via the Output > Type dropdown; every non-None type shares a Value Binding (a state path read from the server) and Value Min/Value Max (the real game-value range that maps onto the visual range below).

Rotate (Needle)

FieldMeaning
Rotation Min/Max°The on-screen angle range the needle sweeps across Value Min-Max.
Smoothing (seconds)The needle eases toward a new reading over roughly this many seconds instead of snapping to it on every update - real analog needles have inertia. 0 disables smoothing for a gauge that should react instantly.
Wobble BindingOptional second state path (e.g. sonar.pulse_hz) that makes the needle shiver around its main position at a rate read from that value - one gauge then shows both an amplitude (where it points, from Value Binding) and a frequency (how fast it shivers, from Wobble Binding) at once.
Wobble Amplitude°How many degrees the shiver swings.
Wobble Speed ScaleShrinks the real Hz value driving the shiver - a raw 0.5-3Hz sonar pulse rate would otherwise be too fast for a human eye to read as a rate; lower this further if it still reads too quick.
Example: engine RPM gauge
Value Binding = engine.rpm_fraction, Value Min/Max = 0/1, Rotation Min/Max = -120°/120°, Smoothing = 0.25s so the needle doesn't jitter with every tick.
Example: sonar dB/pulse dial
Value Binding = sonar.db, Value Min/Max = 0/100, Rotation Min/Max = -60°/60°, Wobble Binding = sonar.pulse_hz, Wobble Amplitude = 8°, Wobble Speed Scale = 0.25 - the needle points at loudness while shivering at a rate that reads as the contact's propeller speed.

Linear (Slider)

FieldMeaning
AxisVertical or Horizontal travel direction.
Travel Min/MaxHow far the sprite physically slides on screen (canvas units) across Value Min-Max.
Example
A fuel gauge float: Value Binding = engine.fuel, Value Min/Max = 0/100, Axis = Vertical, Travel Min/Max = 0/-40 (rising as fuel increases).

Texture Swap (Toggle)

A binary on/off swap rather than a ranged value - shows the object's normal texture when the bound value reads false/off, and Flipped Texture when it reads true/on. No Min/Max fields (there's nothing to range over); the Preview control is a checkbox instead of a slider.

Example
A fuse status light: Value Binding = engine.fuse_blown, Flipped Texture = the blown-fuse sprite.

Visual States

A more general mechanism than Texture Swap above: any number of named states, each overriding sprite/color/rotation/opacity/visibility, selected by matching a live bound value (coerced to a string) against each state's name. Enable via Enable States, set State Binding to the state path to read, then + Add State for each named state a value can take.

FieldMeaning
NameMust exactly match the live value once coerced to a string - e.g. name a state true/false for a boolean binding, forward/neutral/reverse for a gear string, or 2 for a number.
TextureSprite shown in this state, or (none).
ColorFallback plain-color fill used whenever this state has no Texture picked - lets a state be just a color (e.g. an indicator light's empty/loaded/armed colors) without needing a texture asset at all.
Rotation°Added on top of the object's own authored Rotation for this state only - lets a state reuse the exact same sprite turned to a different angle (e.g. a lever's "down" position as its "up" sprite rotated 180°, or a switch's sideways position rotated 90°) instead of needing a second texture asset.
Opacity0-1.
VisibleUnchecking hides the object entirely while this state is active.
DefaultWhich state is shown before any live value has resolved, and the fallback whenever the live value doesn't match any state's name.
Example: reusing one sprite, rotated
A two-position toggle lever with only one piece of art (lever.png, drawn pointing up): add states named false and true, both using lever.png as their Texture, but give true a Rotation of 180° - the lever now visually flips down for its ON reading without importing a second image.
Example: hull damage progression
States NORMAL, DAMAGED, BROKEN, each with its own texture, State Binding pointing at whatever damage-level path the server exposes for that panel.

Toggle Switch Shortcut

Appears once Interaction is set to Click. A packaged shortcut over Visual States for the extremely common on/off-switch case - turning it on automatically enables States with true/false entries pre-created, so there's no need to separately visit the Visual States section and get those names exactly right by hand.

FieldMeaning
State Binding (boolean)The live value that says which state (on/off) is currently active - also becomes the Visual States' State Binding.
Same action turns it on and offChecked (the default for a newly-enabled toggle): the Binding field above is used for both directions, sending its Payload Key as true/false - the common shape for something like SET_ELECTRIC_MOTOR's { active: bool }. Unchecked: ON and OFF are two separate actions with no payload (e.g. START_ENGINE / STOP_ENGINE), and an OFF Binding field appears for the second one.
Default StateON or OFF - which one this control starts showing / falls back to (the same underlying field as Visual States' Default).
ON / OFF TextureOptional distinct sprite per state, same as any other Visual State's Texture field.
Example: single-action toggle
An electric motor switch: Binding = SET_ELECTRIC_MOTOR, "Same action turns it on and off" checked (Payload Key auto-fills to active), State Binding = electrical.electric_motor_active, Default State = OFF.
Example: dual-action toggle
A diesel engine start/stop switch: Binding = START_ENGINE, "Same action turns it on and off" unchecked, OFF Binding = STOP_ENGINE, State Binding = engine.running.

Bindings & Payload Keys

Three related-but-different text fields appear around the inspector, all sharing the same autocomplete data:

FieldDirectionMeaning
BindingEditor → ServerThe server action name sent when the control is clicked/dragged (e.g. SET_RUDDER, FIRE_TORPEDO).
Value Binding / State BindingServer → EditorA dot-path read from the server's broadcast state to drive an Output or Visual State (e.g. sonar.db, engine.running, or an array index like torpedo_tubes.0.state).
Payload KeyEditor → ServerWhich JSON key the control's value is sent under - almost always value (left blank, since that's the server's own default key); picking a known Binding auto-fills this when the action expects something else (e.g. SET_GEAR needs gear, a boolean toggle needs active).
Extra Payload Key / ValueEditor → ServerA SECOND, fixed field sent alongside Payload Key's own value - for an action needing two pieces of data at once, e.g. SET_TUBE_ARMED's {tube: 0, armed: true|false}: Payload Key = armed (the control's own on/off), Extra Payload Key = tube, Extra Payload Value = 0 (constant for this one object - use a separate object per tube). A number-looking Extra Payload Value is sent as a number, otherwise as a string. Leave Extra Payload Key blank for anything that only needs the one Payload Key.

Both autocomplete lists come from SERVER_ACTIONS and SERVER_STATE_PATHS in server-bindings.js - see the Binding Sheet (also linked from the top bar on every page, and from the editor's own toolbar) for the full, filterable, always-current table. It's hand-transcribed from what server/simulation.gd actually implements (apply_input()'s match arms and get_state()'s broadcast shape), not guessed - so wiring a control is "pick a real name from the list" instead of typing a string and hoping it matches. Whenever the server adds, renames, or reshapes an action or state field, that list needs a matching update or autocomplete quietly falls out of sync with reality; the hint text under the Binding field will say a typed name "isn't in the server's known action list" if it can't find a match, which is a good sign the sheet needs updating (or that the name has a typo).

Example: arming one specific torpedo tube
Four Toggle Switch objects, one per tube. Each one: Binding = SET_TUBE_ARMED, Payload Key = armed, Extra Payload Key = tube, Extra Payload Value = 0/1/2/3 (matching that switch's own tube), State Binding = the matching torpedo_tubes.N.armed.

Prefabs

Save as Prefab captures an object's appearance only - type, width, height, color, sprite, pivot, uniform-scale flag (and, for a Group, its children) - as a reusable template, and links this instance to it. Name, position, interaction, and binding are never part of a prefab and stay per-instance. Click a prefab's swatch in the PREFABS list to place another linked instance anywhere. Push Appearance updates the shared template from the currently selected instance and propagates those appearance fields to every other instance linked to the same prefab, across every room and station - useful for "I fixed this switch's artwork, now fix it everywhere." Unlink detaches an instance from its prefab so future pushes stop affecting it.

Example
Build one "Standard Toggle Switch" object, Save as Prefab, then place five instances (fuel pump, battery, radio, bilge pump, compressor), each given its own Binding/Name/position. Later, swap in better switch artwork on any one instance and Push Appearance to update all five at once - their individual bindings are untouched.

Project Backup & the Assets Folder

The editor autosaves to this browser's local storage as you work, but that storage is not reliable long-term (it can silently drop asset image data once its quota fills up, and it's tied to one browser profile). Save Project Backup... downloads a complete snapshot - every room, prefab, and asset's actual image data, with stable IDs - to a file you control; Load Project Backup... restores everything from one exactly as it was, with no risk of assets being reassigned to the wrong images. Save one periodically, and especially before closing the browser for an extended break.

Asset IDs are derived from each file's own relative path within the assets folder (e.g. switches/lever.png), not from load order - so reconnecting or rescanning the same assets folder always reproduces the same IDs for the same files, and existing rooms' sprite references don't break.

Export & Import

Export Room writes the current room's JSON (plus a packed spritesheet PNG covering every asset it actually uses); Export All Rooms does the same for every room at once, into a layouts/-shaped bundle. Either downloads the files, or - once you've used Choose Export Folder... (Chromium browsers only) - writes straight into a chosen folder, e.g. the game client's own layouts/ directory, with no manual save-as step. Import Room JSON loads a previously-exported room's JSON back in as a starting point (note: it restores the room/object layout only, not asset image data - re-scan or re-load the assets folder afterward if the registry is empty).

Validate

Scans the current room's objects and reports problems before they reach the game client: duplicate object IDs, an interactive object with no Binding, a drag control with Min equal to Max, an Output with no Output Binding (or, for a ranged output, Value Min equal to Value Max), a Texture Swap output with no Flipped Texture chosen, and a Station Link spawn with no target station picked. Run it before exporting a room you haven't touched in a while.
